# Qwen 小模型与 Jev 远程实验方案 v1

日期：2026-10-13（Asia/Shanghai）。状态：本地代码准备阶段，真实实验尚未开始。

研究问题：在统一意图选择任务中，Qwen3-0.6B 和 Jev 的语义质量、端到端性能、成本及候选类别扩展表现如何？本方案不预设任何模型胜出，也不宣称提出新模型或算法。

## 证据目标

| 目标 | 最低证据 | 对应实验 |
|---|---|---|
| C1：识别两模型的质量与部署成本权衡 | 同测试集、同目录、逐请求日志、配对比较、真实价格、明确服务器与网络 | B1、B2、B3 |
| C2：解释候选集合扩大时的质量与成本变化 | 每个种子固定共同样本、嵌套目录、多次候选抽样 | B4 |

需要排除的解释：数据/类别定义不同、失败被删掉、Qwen 输出截断、网络条件变化、样本难度变化、缓存默认开启、使用演示价格、把重复调用当作新增独立样本。

## 固定比较条件

- 主模型：Qwen/Qwen3-0.6B、Jev。Jev 配置暂沿用 jev-1.13.0，正式启动前核实该版本和真实接口契约。BERT 和更多 Qwen 尺寸暂不加入主矩阵。
- 主数据：MASSIVE 1.1，默认 en-US。原始 train/dev/test 分区保持不变；300 条分层验证子集仅用于 checkpoint。最终质量评测使用完整 test。
- 类别目录：人工审阅准确且有区分度的说明；两模型共享内容和顺序。开发/修订只使用训练集或验证集，不根据最终测试错误修改本轮目录。
- 训练条件：Qwen 和 Jev 均作为现成模型进行选择；本轮不微调 Qwen。若后续加入 BERT，需单独说明监督训练条件。
- Qwen：BF16，temperature=0，关闭 thinking，max_tokens=64，仅接受合法 JSON 标签；上下文先设 4096，但必须用同 revision 的 tokenizer 检查所有输入加输出预算。超限时在实验开始前统一提高窗口并重新冻结。
- 缓存：主实验显式关闭 Qwen prefix caching；不使用应用层请求缓存。Jev 内部缓存和硬件不可观测，列为限制。后续启用缓存时另建实验版本，不混入主表。
- 模型 revision、vLLM 镜像 digest、GPU 型号/驱动/功率、CPU、部署参数、Controller 位置和 API 配额固定并记录。
- 首选同一个独立 Controller 调用 Qwen 和 Jev。也允许远程服务器同时运行 Controller 与 Qwen：先确认 Controller CPU/调度余量，记录这一拓扑；若有明显调度迟滞，迁移 Controller 后重测。
- 本地 Qwen 与外部 API 的结果解释为端到端部署表现，不解释为网络无关的纯模型推理速度。

## B1：质量与错误分析（必做）

问题：面对相同意图目录，两模型的正确率、逐类表现和失败方式有何区别？

1. 各运行 300 条验证样本，Qwen 预热 50 条、Jev 预热 5 条。预热单独记录，但计入 API 请求预算和实际账单。
2. checkpoint 通过条件：样本齐全、无非法类别、日志可复算、版本与输入冻结。接口故障先在验证阶段修复；真实语义错误不属于链路故障。
3. 完整测试集，每模型重复 3 次，重复编号 1/2/3。固定模型参数，记录 API 是否存在重复预测波动。
4. 指标：全部请求 Accuracy、完整目录 Macro-F1、逐类 precision/recall/F1、合法成功率、状态分布。失败计入 Accuracy 分母及对应类别 FN。
5. 两模型按 sample_id 配对，报告两者都对、仅 Jev 对、仅 Qwen 对、两者都错的数量；给出配对准确率差与 bootstrap 95% 区间。
6. 每轮独立报告，重复请求不合并成 3N 个独立样本。Wilson 区间针对固定模型的样本正确率；bootstrap 以配对样本为单位、固定 seed=42、2000 次。
7. 人工审阅 30–50 个代表案例，覆盖高频混淆类别、两种单模型正确组、两者都错和接口失败。描述抽样规则，保留原始文本、真值和预测。

验收是完整、可复算的证据，不设置“Jev 必须优于 Qwen”这样的结果门槛。

图表：主质量表、混淆矩阵、逐类差异、代表错误案例。输出 runs.csv、paired-comparisons.csv、error-cases.csv 和逐类/混淆 CSV。

## B2：性能与负载（必做）

问题：在统一成功率和延迟目标下，每种部署可以持续处理多少有效请求？

- 数据：完整测试集有放回抽样；两模型每轮使用同 seed 和请求时间表。
- 开放环固定速率：1/2/4/8 RPS，最大客户端并发 32，timeout=30s。
- 每配置预热：Qwen 50、Jev 5。发送窗口初测 120s；正式容量实验改为至少 300s，必要时 600s。
- 重复 3 次，seed=42/43/44；每轮打乱 RPS 次序且两模型顺序一致，run 间冷却 30s。不同模型串行执行，GPU 上只运行被测模型。
- 主 SLO=500ms，合法成功率要求 >=99%，最大 Controller 调度迟滞 <=20ms。若业务需要 200ms 或 1000ms，另建对应版本；这些是待确认的目标，不是模型结果。
- 记录 attempted 和 successful 延迟分位数、错误/超时/client_overload、Goodput、Correct Goodput、调度迟滞。延迟从计划到达到完成，包含客户端及网络。
- 先完成同输入/目录的 main 质量基线，套件才允许启动 load。结果是否满足业务最低 Accuracy/F1 由实验者按事先确定的要求判断。
- 容量候选必须各次重复均满足成功率/SLO/调度要求，另通过质量要求和更长稳态检查。保守选择重复实验中最小有效吞吐，不取一次峰值直接作为月度容量。
- 120s 与 300s 的数据必须分开分析。正式容量附近再做分段稳态检查；当前代码输出全窗口指标，尚未自动给出稳态分段结论。
- 若 8 RPS 仍有余量，再补 16/32 等负载点；先核实 API 的 RPS、Token/s 配额，429 单独统计。不要根据单个失败点盲目提高 Jev 压力。

图表：RPS—p95、RPS—Correct Goodput，重复结果均值、标准差及范围。延迟 p99 在低 RPS 短窗口下样本较少，报告样本数和限制。

## B3：成本（必做，离线核算）

问题：在相同任务与流量场景下，API 和常驻 GPU 的费用差异是什么？

- 按真实 API 单价和实际 usage 核算 Jev；价格来自当前账户计费条款，保留来源、日期和账单对账。超时可能已计费，usage 缺失时仅给下界。
- Qwen 按整台实例的真实小时价核算测量窗口加排空时间。相同机器用作 CPU/Controller 时需说明整机成本范围。
- 分别输出每百万 successful 和 SLO-valid 请求成本。实例空闲、启动、下载、预热不在测量成本里，放进总租赁账单或月度 TCO。
- 两者换算到同一币种；API 与 GPU 原币不同则采用相同汇率日期。价格模板中的 null/TODO 必须填写，演示价不能作为报告数据。
- 月度场景暂设 1万/10万/100万请求，峰值 1/2/8 RPS，730 小时常驻，目标利用率 0.7；场景待用户确认。
- Qwen 副本数根据经过独立验收的可持续容量向上取整。API 月费用使用 main 测试集的平均已知 Token 成本估算，须说明未来业务文本/目录长度假设，并另核实峰值配额。
- cost_analysis 写独立 cost.json，分析和汇总优先使用该结果，原 summary.json 不改写。

图表：单请求成本表、月度场景对照；费用未知或 usage 不完整时明确留空/下界。

## B4：候选类别规模（重点扩展）

问题：增加干扰类别是否改变质量、输入长度、响应时间和费用？

- 候选数 10/30/60；种子 42/43/44。
- 每个种子从支持足够样本的类别中选 10 个 anchor 类，每类选 20 条 test 样本，共 200 条。每个候选规模使用完全相同的 200 条样本。
- 30/60 类在 10 个 anchor 类之外增加随机干扰类，目录集合嵌套；共同类别的说明和相对顺序保持一致。
- 不同种子更换 anchor/干扰目录和对应冻结样本；每个种子内做配对比较，跨种子报告均值及范围，不把它们冒充同一固定任务的重复调用。
- 指标：Accuracy、macro_f1_supported_classes、延迟、usage、费用；完整目录 Macro-F1 保留但不用于跨规模主比较，因为新增无真值支持类别置零会人为降低该指标。
- 所有样本的真值始终在目录中。不能为每个规模分别重抽样，不能加入模型生成的真值。

图表：候选数—质量、候选数—延迟、Token/费用表。结果解释为固定 anchor 分类任务增加干扰类别的效应，不代表每个规模完整类别覆盖的总体准确率。

## B5：类别说明消融（可选）

问题：更详细的候选说明带来的质量收益是否值得额外输入和费用？

- 同一完整测试集、同一类别集合与顺序，对比 brief/detailed/boundary 三份人工审阅的说明。
- 使用 train/dev 开发说明并冻结；禁止从当前 test 错误反向编写说明再汇报同一 test 的无偏结果。
- 两模型每种说明各测一轮，预算允许可改为 3 轮。先检查所有描述版本的上下文长度。
- 模板默认 disabled；用户完成三个 mapping JSON 后再启用。
- 输出质量/用量/延迟/成本变化，不添加未经验证的阈值校准、重训或拒识结论。

## 数量和预算

默认启用 checkpoint/main/load/scale，共 50 个 run：2 + 6 + 24 + 18。description 可选增加 6 个 run（每版本一轮）。

设完整测试集大小为 N，120s 初测版本的 Jev 最大请求数为 3N + 7625：checkpoint=305、main=3(N+5)、load=5460、scale=1845。预算包括所有预热，实际发送可能因客户端拒绝略低；不能把预算当作价格或费用。

load 双模型测量窗口合计 48 分钟，Qwen 单模型窗口合计 24 分钟；还要加预热、排空、冷却、质量实验和服务器租赁空闲。正式 300s 版本的双模型窗口合计 2 小时，Jev 总请求上限为 3N + 15725。实际吞吐和耗时未知，质量时间用 pilot 测得每请求耗时估算：3N×每请求平均耗时。

推荐 GPU 起点：NVIDIA 12–16GB，用于 0.6B 低/中并发；24GB 便于扩展。实际上下文、并发、vLLM 运行缓冲区决定是否足够，先小规模验证。Jev 无需本地 GPU。

## 启动前待确认

1. MASSIVE 语言是否保持 en-US，是否只做 Qwen3-0.6B + Jev。
2. GPU 服务器型号/显存、Linux/驱动/容器条件；Controller 独立还是同机。
3. 当前可用 Jev 版本、RPS/Token 配额、付费预算和实际价格；密钥只在服务器终端设置。
4. 是否按 500ms SLO、99% 成功率；业务最低 Accuracy/F1 要求；正式负载窗口和扩展负载点。
5. 类别说明审阅完成状态，以及是否启用 B5。

## 结果边界

- 当前只有本地 Mock/fixture 验证，不构成真实 Qwen/Jev 跑分。
- 外部 API 的硬件与服务策略不可完全固定；记录版本、时间、区域和返回的 request ID。
- 数据分层子集、实际业务输入分布和 API 计费制度不同，必须限制外推。
- 缓存消融、BERT/INT8、OOS/拒识、动态重训和新模型尺寸留在后续计划。
